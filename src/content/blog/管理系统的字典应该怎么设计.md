> 管理系统的字典应该怎么设计？

如果你说的是 **Admin 管理系统里的“字典配置”**，我建议把它理解成：

> **把那些“经常作为选项出现，但又不值得写死在代码里的枚举数据”配置到数据库里。**

比如：

```text
用户状态
  1 → 正常
  2 → 禁用

性别
  1 → 男
  2 → 女
  0 → 未知

订单状态
  pending → 待支付
  paid → 已支付
  cancelled → 已取消
```

但这里有一个很重要的设计点：

## 1. 不要把“字典”和“配置”混为一谈

我建议你的 Admin Core 分成两个概念：

### 字典 Dictionary

描述：

> **一组可选值**

例如：

```text
user_status
├── active   正常
└── disabled 禁用

gender
├── male     男
├── female   女
└── unknown  未知
```

### 系统配置 Config

描述：

> **一个系统参数**

例如：

```text
site.name = "My Admin"
site.logo = "..."
security.session_timeout = 7200
upload.max_size = 10485760
```

所以：

```text
字典 = 一个 key 对应多个 option
配置 = 一个 key 对应一个 value
```

---

# 2. 字典表怎么设计？

最简单我建议两张表。

### `sys_dict_types`

表示“字典类型”：

```text
id
code
name
description
status
created_at
updated_at
```

例如：

```text
id: 1
code: user_status
name: 用户状态
```

---

### `sys_dict_items`

表示具体选项：

```text
id
dict_type_id
value
label
sort
status
extra
created_at
updated_at
```

例如：

```text
dict_type
    user_status

items
────────────────────
value       label      sort
active      正常        1
disabled    禁用        2
```

其中：

```text
value
```

给程序用。

```text
label
```

给用户看。

---

# 3. 为什么不要直接存 `1、2、3`？

比如：

```text
1 = 正常
2 = 禁用
```

当然可以。

但我更推荐：

```text
active = 正常
disabled = 禁用
```

因为后端代码：

```go
if user.Status == "disabled" {
    ...
}
```

比：

```go
if user.Status == 2 {
    ...
}
```

可读性好很多。

当然，如果某些业务天然使用整数状态码，也可以使用：

```text
value = "1"
value = "2"
```

**字典系统不要强制 value 必须是 int。**

把它当成字符串通常更通用。

---

# 4. `extra` 很有用

比如：

```json
{
  "value": "active",
  "label": "正常",
  "extra": {
    "color": "green"
  }
}
```

前端就可以：

```text
active → 正常 → green
```

另一个：

```json
{
  "value": "disabled",
  "label": "禁用",
  "extra": {
    "color": "red"
  }
}
```

这样你的 Arco `<Tag>` 就可以根据字典配置决定展示效果。

不过这里要注意：

> `extra` 适合放**展示元数据**，不要把核心业务规则全塞进去。

# 5. API 怎么设计？

你现在采用 OpenAPI，我会设计成：

```http
GET /api/dict/{code}
```

例如：

```http
GET /api/dict/user_status
```

返回：

```json
{
  "code": "user_status",
  "name": "用户状态",
  "items": [
    {
      "value": "active",
      "label": "正常",
      "sort": 1,
      "extra": {
        "color": "green"
      }
    },
    {
      "value": "disabled",
      "label": "禁用",
      "sort": 2,
      "extra": {
        "color": "red"
      }
    }
  ]
}
```

前端可以非常自然地：

```tsx
const { data } = useDict("user_status")
```

然后：

```tsx
<Select options={data?.items} />
```

# 6. 管理后台本身怎么管理？

你的 Admin 可以有：

```text
系统管理
├── 用户
├── 角色
├── 权限
├── 字典
├── 系统配置
└── 操作日志
```

进入：

```text
字典管理
```

看到：

```text
┌─────────────────────────────────────┐
│ 字典类型                            │
├──────────────┬──────────┬───────────┤
│ 名称         │ Code     │ 状态      │
├──────────────┼──────────┼───────────┤
│ 用户状态     │ user_status │ 启用   │
│ 性别         │ gender       │ 启用   │
│ 文件类型     │ file_type    │ 启用   │
└──────────────┴──────────┴───────────┘
```

点进去：

```text
用户状态

┌──────────┬──────────┬──────┬──────┐
│ Value    │ Label    │ 排序 │ 状态 │
├──────────┼──────────┼──────┼──────┤
│ active   │ 正常     │ 1    │ 启用 │
│ disabled │ 禁用     │ 2    │ 启用 │
└──────────┴──────────┴──────┴──────┘
```

# 7. 但这里有一个很重要的坑

**不是所有枚举都应该做成字典。**

例如：

```go
type UserStatus string

const (
    UserStatusActive   UserStatus = "active"
    UserStatusDisabled UserStatus = "disabled"
)
```

这种**核心业务状态**，我反而建议保留在代码里。

因为：

```text
订单状态
支付状态
任务状态
```

这些往往不是“管理员随便增加一个选项”就可以的。

比如管理员突然在后台增加：

```text
order_status = "flying"
```

你的后端业务代码根本不知道怎么处理。

所以应该区分：

### 代码枚举

```text
业务规则依赖
不能随便增加
```

例如：

```text
订单状态
支付状态
任务状态
```

### 数据字典

```text
主要用于展示/选择
可以由管理员维护
```

例如：

```text
性别
地区
职位
用户来源
客户等级
标签
文件类型
```

---

# 8. 对你这个 Admin Core，我建议最终做成这样

```text
Admin Core
│
├── Auth
├── RBAC
├── User
├── Operation Log
│
├── Dictionary
│   ├── DictType
│   └── DictItem
│
└── Config
    └── ConfigItem
```

数据库：

```text
sys_users
sys_roles
sys_permissions
sys_user_roles
sys_role_permissions

sys_operation_logs

sys_dict_types
sys_dict_items

sys_configs
```

这样非常干净。

### 再往前一步

我甚至建议你的前端不要到处写：

```tsx
<Select>
  <Option value="active">正常</Option>
  <Option value="disabled">禁用</Option>
</Select>
```

而是统一：

```tsx
<DictSelect code="user_status" />
```

表格里：

```tsx
<DictLabel code="user_status" value={user.status} />
```

这样**字典就真正成为 Admin Core 的基础设施**了。

不过要注意：**字典适合解决“可配置的选项”，不应该变成一个万能的动态业务规则系统。** 这是设计字典系统时最容易踩的坑。
