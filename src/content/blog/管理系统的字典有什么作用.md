> 管理系统的字典有什么作用

可以把**字典（Dictionary）理解成：把系统里“可选的、经常重复出现的值”集中管理起来。**

比如你的管理系统里经常会出现：

```text
用户状态：
正常
禁用

性别：
男
女
未知

用户来源：
官网
广告
朋友推荐
活动
```

如果这些东西全部硬编码在前端：

```ts
const statusOptions = [
  { value: "active", label: "正常" },
  { value: "disabled", label: "禁用" }
]
```

以后想增加一个“冻结”，就得改代码、重新发布。

**字典就是把这些选项放到数据库里，让系统可以动态读取。**

---

### 它解决的核心问题

可以概括成一句话：

> **把“程序代码中的固定选项”变成“系统可以配置的选项”。**

例如：

```text
sys_dict_types

user_status
用户状态
```

下面有：

```text
active     正常
disabled   禁用
frozen     冻结
```

前端只需要：

```text
GET /api/dict/user_status
```

就能拿到：

```json
[
  { "value": "active", "label": "正常" },
  { "value": "disabled", "label": "禁用" },
  { "value": "frozen", "label": "冻结" }
]
```

于是前端的 Select、Table、Form 都可以复用。

---

### 为什么管理系统特别需要字典？

因为后台系统有大量这种东西：

```text
用户状态
订单来源
客户等级
性别
学历
职位
行业
地区
标签类型
文件类型
通知类型
```

它们有一个共同特点：

**“选项比较稳定，但又希望管理员能够调整。”**

所以可以做成：

```text
              字典
               │
       ┌───────┼───────┐
       ↓       ↓       ↓
    用户状态   性别    客户等级
       │       │       │
   正常/禁用  男/女    普通/VIP
```

这样业务系统不用每个地方自己维护一套 options。

---

### 但有一个非常重要的区别

**不是所有状态都应该做成字典。**

例如：

```text
订单状态：

待支付
已支付
已发货
已完成
已取消
```

如果你的后端代码明确写了：

```go
if order.Status == "paid" {
    // 扣库存
}
```

那么这个状态其实属于**业务逻辑的一部分**。

这时候不应该让管理员在后台随便增加：

```text
"超级已支付"
"半支付"
"差不多支付"
```

因为代码根本不知道怎么处理。

所以：

| 类型   | 是否适合字典 |
| ---- | ------ |
| 性别   | ✅      |
| 用户来源 | ✅      |
| 客户等级 | ✅      |
| 职位   | ✅      |
| 标签类型 | ✅      |
| 订单状态 | 通常 ❌   |
| 支付状态 | 通常 ❌   |
| 任务状态 | 通常 ❌   |
| 权限类型 | 通常 ❌   |

**判断标准：**

> 如果这个值只是“给用户选、给页面展示”，适合字典。
> 如果这个值会直接决定程序怎么运行，通常应该是代码里的 Enum/常量。

所以你可以把 Admin Core 里的字典理解成：

> **一个统一的、可配置的 Options 管理中心。**

这也是为什么前端可以进一步封装成：

```tsx
<DictSelect code="user_status" />
<DictLabel code="user_status" value={user.status} />
```

业务页面甚至不需要关心这些选项具体从哪里来的。
